# rs_cdr_generator

Генератор синтетических CDR (CALL/SMS/DATA) для нагрузочных прогонов
batch-scoring — Rust-порт python-генератора. Подробности формата и принятых
упрощений — `docs/field-mapping.md`.

## Сборка образа для изолированного контура

Контур air-gapped: интернета нет, `crates.io` недоступен, сборка внутри
контура должна пройти без единого обращения в сеть.

1. На машине **с** интернетом, один раз, зафиксировать и скачать зависимости:

   ```bash
   cargo vendor vendor        # раскладывает крейты из Cargo.lock в vendor/
   ```

   Каталог `vendor/` (~140 МБ) в git не хранится — он не диффается и не несёт
   пользы в истории; воспроизводимость держит закоммиченный `Cargo.lock`.
   `.cargo/config.toml` уже настроен подставлять `vendor/` вместо `crates.io`.

2. Каталог `vendor/` переносится в контур вместе с исходниками (тем же
   архивом/образом поставки, что и остальной контур) и кладётся рядом
   с `Dockerfile` перед сборкой.

3. Сборка образа — уже в контуре, без сети:

   ```bash
   docker build -t rs-cdr-generator:contour .
   ```

   `Dockerfile` — многоступенчатый: `cargo build --release --locked --offline`
   в builder-слое (используется исключительно `vendor/`), в итоговый образ
   попадает только бинарник.

## Запуск

```bash
# 1. База абонентов (один раз, переиспользуется между прогонами)
docker run --rm -v $(pwd)/data:/data rs-cdr-generator:contour \
  generate-subscribers --output /data/sub.redb --size 20000 --seed 42

# 2. Генерация CDR за период
docker run --rm -v $(pwd)/data:/data rs-cdr-generator:contour \
  generate-cdr --subscriber-db /data/sub.redb --start 2025-01-01 --days 32 \
  --out /data/out --workers 2 --seed 42
```

## Параметры памяти и скорости

- `--workers N` — размер пула `rayon` для генерации CDR. Пик RSS зависит и от
  числа воркеров, и от длины периода (`--days`), но зависимость от периода
  резко сублинейна: на измерении в `docs/field-mapping.md` (раздел «Байт RSS
  на запись при росте периода») период вырос в 64 раза (2 → 128 дней), а пик —
  в 7.5 (317 МБ → 2381 МБ); 58.5 млн записей укладываются в 2.4 ГБ. Для
  сравнения, питоновская версия расходует ~385 байт на запись независимо
  от объёма и на тех же 58.5 млн записей потребовала бы порядка 22 ГБ.
  Рычаг «уменьшить `--workers` — снизить пик памяти ценой скорости» остаётся
  в силе, но бюджет памяти нельзя планировать одной формулой без длины периода.
- Прогон на большее число `--workers` быстрее (линейно до ~8 воркеров на
  проверенном профиле), но пропорционально дороже по памяти — выбирать
  `--workers` по доступной памяти хоста, а не по числу его ядер.
- `--rotate-bytes` — предел размера файла до ротации (актуально при долгих
  прогонах: ограничивает объём одного `.csv.gz` до архивации).

## Поставка в реестр контура

### 🔴 `0.1.0` — НЕ ИСПОЛЬЗОВАТЬ, содержит дефект целостности

При параллельной записи несколько writer-задач одного прогона маршрутизировались
по `msisdn` вместо `serving_ne_id`, и это позволяло двум задачам писать в один
и тот же файл трафика данных (`sgw_data`/`pgw_data`) одновременно — итоговый
`.csv.gz` усекался. На боевом прогоне не проходили `gzip -t` 480 из 1200
файлов (40 %). Отказа при этом не было: прогон завершался успешно, объём выхода
выглядел правдоподобным, обнаружить порчу можно было только целевой проверкой
целостности архивов. Починка — коммит `052f719` (маршрутизация по
`serving_ne_id`). Образ `0.1.0` в реестре оставлен как есть (переписывать теги
молча нельзя), но использовать его нельзя — заменяется версией `0.1.1`.

### Устранение хардкода (2026-09-08, вторая правка)

Секции, которые раньше **игнорировались** (значение из конфига не долетало
до генератора, использовался дефолт кода), теперь читаются типизированно
(`src/contour.rs`) и применяются (`src/config.rs::apply_contour_config`,
`generators.rs`, `contact_book.rs`, `main.rs`):

| Было в дефолтах (зашито в коде) | Стало из конфига |
|---|---|
| `call_dispositions` ANSWERED=0.82 фиксированно | `events.voice.success_rate` → ANSWERED=`success_rate`, остаток делится в прежней пропорции между NO ANSWER/BUSY/FAILED/CONGESTION |
| SMS status-веса `[0.1, 0.88, 0.02]` фиксированно | `events.sms.delivery_success_rate` → DELIVERED=`success_rate`, остаток делится 5:1 между SENT/FAILED |
| `contact_book::EXTERNAL_CALL_RATIO=0.15` (расходилось с конфигом, где 0.12) | `subscribers.contact_book.external_call_ratio` |
| `contact_book::{ZIPF_A, MIN_DEGREE, MAX_DEGREE, REPEAT_CALL_PROBABILITY}` | `subscribers.contact_book.degree_distribution.params.{a,min,max}`, `repeat_call_probability` |
| Внешний номер — равновероятный `cfg.prefixes` | `subscribers.external_numbers.prefixes[].weight` (`WeightedIndex`) |
| Объём data-сессии — `Normal` по RAT (1–12 МБ, зашито) | `events.data.volume_uplink`/`volume_downlink` (lognormal `mu`/`sigma`/`min_bytes`) |

{hourly_weights,mobility,imei_tac_pool,rat_preference}` (`day_of_week_multipliers`

`subscribers.imsi_prefix`/`msisdn_prefix`, `meta.output.*`/`meta.parallelism.*`,

**Проверено контурным конфигом (12 000 абонентов, 240 суток,
`demo-cdr.yaml` с `total_count: 12000`, идентичным прежнему замеру):**

- `gzip -t` — 0 битых из 1200 файлов;
- записей: **40 735 882** (mo_call 8 989 534, mt_call 8 891 930, mo_sms
  4 010 249, mt_sms 3 966 809, sgw_data=pgw_data 7 438 680) — против прежних
  38 789 435 (было) и питоновских 38 218 984. `mo_call`/`mt_call` теперь
  почти симметричны (0.989 против прежних 0.84) — прямое следствие починки
  внешнего `mt_call`, а не подгонки;
- объём выхода: **1 352 869 293** байт против прежних 1 343 290 082 и
  питоновских 1 881 417 409 — доля от питона практически не сдвинулась

  не дал ожидаемого сдвига, не подтвердилась подгонкой каких-либо
  коэффициентов — сдвига по общему байтовому итогу просто нет, при этом
  средний `downlink_volume_bytes` в контрольном прогоне (200 абонентов)
  соответствует lognormal(12.5, 0.8) с точностью до сэмплирования (мера
  верна, метрика зависит не от неё). **Вероятная причина** −28 % —
  не объём data-полей, а систематически пустые CDR-поля из
  `docs/field-mapping.md` (`sequence_number`, `consolidation_id`,
  `charging_id`, `redirecting_number`, `answer_timestamp`,

  не входившие в задание этой правки и не проверенные здесь количественно.
  **Не подтверждено, требует отдельного замера длины строки на пару
  записей rust/питон.**

`success_rate` теперь реально управляет диспозицией звонка (описанная
выше пропорция), но разложение асимметрии 88 %/12 % из задания сверить
не удалось: `cause_for_termination`/диспозиция не экспортируется в CSV
(`field-mapping.md`, «у rust — только текстовая причина, не пишется в
файл») — измерить долю ANSWERED/неуспеха по выходным файлам напрямую
нельзя без отдельной инструментации. Осталось непроверенным.

### Гейт MT по success_rate и заполнение трёх колонок (2026-09-08, четвёртая правка)

Две правки: (1) MT-запись теперь порождается только при диспозиции
ANSWERED — `generate_forced_direction` возвращает признак успеха,
`worker_generate_shard` пропускает MT для несостоявшегося вызова
(было: MT порождался безусловно, `mt_call`/`mo_call` уходил к 0.989);
(2) заполнены `consolidation_id` (случайная 32-hex метка корреляции
MO/MT, CALL и SMS), `answer_timestamp` (`event_timestamp+1с` для
ANSWERED CALL, по правилу питона) и `charging_id` (случайный `u32`,
общий у `sgw_data`/`pgw_data` пары) — измерение на питоновском образце
показало, что 8 пустых колонок объясняют весь разрыв объёма 28.1 %
с запасом (детали и методика — `docs/field-mapping.md`, «Измерение
пустых колонок»). Оставшиеся пустыми `sequence_number`,
`redirecting_number`, `vendor_extensions` — не расхождение, у питона
на `demo-cdr.yaml` тоже пусто; `cause_for_termination`/`qci` — долг,
у питона источник числовой и конфижный, а rust эти секции не читает.

**Проверено контурным конфигом (12 000 абонентов, 240 суток,
`demo-cdr.yaml`, тот же конфиг что и в замере выше):**

- `gzip -t` — 0 битых из 1200 файлов, wall 305 с, пик RSS 3 219 759 104
  байт (≈3,00 ГиБ, `/usr/bin/time -l`, 6 воркеров);
- записей: **39 355 984** (mo_call 8 989 511, mt_call 7 553 271,
  mo_sms 4 007 806, mt_sms 3 963 780, sgw_data=pgw_data 7 420 808) —
  против питоновских 38 218 984 (+2,98 %). `mt_call`/`mo_call` = **0,840**
  (питон ~0,85, было 0,989 до этой правки) — гейт по success_rate
  сработал;
- объём выхода: **1 957 020 374** байт против питоновских 1 881 417 409 —
  **+4,02 %** (было −28,1 % до заполнения трёх колонок). Заполнение
  перекрыло разрыв с запасом, а не закрыло его точно — ожидаемо: замер
  на образце (`field-mapping.md`) уже показывал, что обнуление тех же
  8 колонок даёт 31,66 % экономии сжатого объёма против измеренных
  28,1 %, то есть заполнение всех трёх должно было и перекрыть разрыв.
  Осталось непроверенным, какая доля +4,02 % — от `consolidation_id`
  (высокоэнтропийная случайная строка, плохо сжимается) против
  `answer_timestamp`/`charging_id`;
- доли по группам (запись-к-записи, не байт): голос 42,04 % (питон
  39,5 %), SMS 20,26 % (питон 20,3 %, совпадает), data 37,71 % (питон
  40,2 %) — SMS сходится точно, голос/data разошлись на 2,5 п.п. в
  разные стороны; причина не разбиралась, не входило в задание.

### Проведён `day_of_week_multipliers` (2026-09-08, шестая правка)

Последнее известное расхождение с питоном (голос/данные разошлись на 2,5 п.п.
в разные стороны, раздел выше) — гипотеза: `day_of_week_multipliers` профиля
не читался вовсе (поля не было в структуре конфига), а у питона
(`demo/generator/upstream/cdr_generator/engine/rates.py:60-63`) он масштабирует
`hourly_rate` отдельно по voice/data/sms.

**Расчёт до правки** (взвешенное среднее по всем профилям и фактическому
распределению дней недели в периоде 05.03–30.10.2025, 240 суток, начало —
среда): без множителя доли голос/SMS/data = 48,85/25,49/25,66 %, с множителем
— 46,96/25,75/27,29 % — сдвиг голоса −1,89 п.п., data +1,63 п.п., того же
знака и порядка, что наблюдаемое расхождение 2,5 п.п. Гипотеза подтверждена
расчётом до правки, не подгонкой после.

Параметр проведён типизированно: `DayOfWeekMultipliersCfg` (`src/contour.rs`),
поля `dow_mult_{voice,sms,data}: [f64; 7]` у `SubscriberProfile`
(`src/config.rs`), множитель применяется к суточной лямбде профиля ДО
сэмплирования Пуассона, по дню недели текущего шарда (`src/generators.rs`,
`worker_generate_shard`, `dow_idx = day.weekday().num_days_from_monday()`).

🔴 **Тупик, на котором потеряно ~40 минут: правка временно проверялась через
`git stash && cargo test …; git stash pop`**, чтобы отделить преждевременный
дефект теста от своей правки — это откатывает исходники, а последующий
`cargo test --release` пересобирает `.rlib` уже БЕЗ правки; следующий сразу за
этим прогон `generate-cdr` без промежуточного `cargo build --release`
использовал результат этой пересборки, и полный прогон 12000/240 показал
почти плоское распределение по дням недели (эффект как будто исчезал на
большом объёме). Прогоны по 3/6/20/60/120/200 суток тем же бинарником

## Отличие от питоновского `cdr-generator`, который использует роль `bs_cdr_gen`

- **Другой бинарник.** Питоновский образ `qa/cdr-generator:0.1.0-py3.11`
  (`installer/roles/bs_cdr_gen/defaults/main.yml:97-98`) — CPython, этот —
  нативный `rs_cdr_generator` (33.5 МБ, статически подтянутый только к
  системной glibc `debian:bookworm-slim`, сети при запуске не требует).
- **Другие флаги CLI.** У rust-версии два раздельных шага —
  `generate-subscribers` (база абонентов в `redb`) и `generate-cdr` (сама
  генерация с `--subscriber-db`); у питоновской, по `demo/generator/README.md`,
  разбивки на такие подкоманды нет. Общий конфиг (`--config path.yaml`)
  подключается тем же принципом «CLI override поверх файла».
- **Формат вывода совместим по контракту.** Тот же `CDR_{ne_id}_{date}.csv.gz`
  и тот же набор колонок CSV (проверено смоук-прогоном ниже) — партиционирование
  по `ne_id`/дате и путь `<out>/<ne_id>/CDR_<ne_id>_<date>.csv.gz` совпадают.
- **🔴 Взаимозаменяемость НЕ подтверждена.** Сверка данных питон↔rust
  не завершена — по состоянию на 2026-09-08 идёт проверка по типам трафика,
  в частности не выяснено, совпадает ли в rust-версии доля SMS с той, что
  у потребителя (SMS — 20.2 % набора у потребителя). Смоук этой сборки
  (50 абонентов, 2 суток) SMS-записи произвёл (`mo_sms`/`mt_sms` есть в
  выводе), но это не заменяет сверку долей и распределений. **Замена
  питоновского генератора в `bs_cdr_gen` этим образом сейчас НЕ предлагается,
  роль не трогалась.**

  🔴 **Ограничение важнее статуса сверки: замена не предлагается даже
  после того, как сверка будет завершена, пока не сменится набор данных.**
  Текущий набор `signal-v2` сделан питоновской версией, и разметка построена
  по нему — менять генератор под уже зашитый сигнал нельзя. Сопоставимость
  данных двух версий подтверждена сверкой (круги общения, доли трафика, SMS,
  парность data-сессий), но это утверждение про **следующий** набор данных,
  а не про текущий `signal-v2`.
