# rs_cdr_generator

Генератор синтетических CDR (CALL/SMS/DATA) для нагрузочных прогонов
batch-scoring — Rust-порт python-генератора. Подробности формата и принятых
упрощений — `docs/field-mapping.md`.

## Сборка образа для изолированного контура

Контур air-gapped: интернета нет, `crates.io` недоступен, сборка внутри
контура должна пройти без единого обращения в сеть.

1. На машине **с** интернетом, один раз, зафиксировать и скачать зависимости:

   ```bash
   cargo vendor vendor        # раскладывает крейты из Cargo.lock в vendor/
   ```

   Каталог `vendor/` (~140 МБ) в git не хранится — он не диффается и не несёт
   пользы в истории; воспроизводимость держит закоммиченный `Cargo.lock`.
   `.cargo/config.toml` уже настроен подставлять `vendor/` вместо `crates.io`.

2. Каталог `vendor/` переносится в контур вместе с исходниками (тем же
   архивом/образом поставки, что и остальной контур) и кладётся рядом
   с `Dockerfile` перед сборкой.

3. Сборка образа — уже в контуре, без сети:

   ```bash
   docker build -t rs-cdr-generator:contour .
   ```

   `Dockerfile` — многоступенчатый: `cargo build --release --locked --offline`
   в builder-слое (используется исключительно `vendor/`), в итоговый образ
   попадает только бинарник.

## Запуск

```bash
# 1. База абонентов (один раз, переиспользуется между прогонами)
docker run --rm -v $(pwd)/data:/data rs-cdr-generator:contour \
  generate-subscribers --output /data/sub.redb --size 20000 --seed 42

# 2. Генерация CDR за период
docker run --rm -v $(pwd)/data:/data rs-cdr-generator:contour \
  generate-cdr --subscriber-db /data/sub.redb --start 2025-01-01 --days 32 \
  --out /data/out --workers 2 --seed 42
```

## Параметры памяти и скорости

- `--workers N` — размер пула `rayon` для генерации CDR. Пик RSS зависит и от
  числа воркеров, и от длины периода (`--days`), но зависимость от периода
  резко сублинейна: на измерении в `docs/field-mapping.md` (раздел «Байт RSS
  на запись при росте периода») период вырос в 64 раза (2 → 128 дней), а пик —
  в 7.5 (317 МБ → 2381 МБ); 58.5 млн записей укладываются в 2.4 ГБ. Для
  сравнения, питоновская версия расходует ~385 байт на запись независимо
  от объёма и на тех же 58.5 млн записей потребовала бы порядка 22 ГБ.
  Рычаг «уменьшить `--workers` — снизить пик памяти ценой скорости» остаётся
  в силе, но бюджет памяти нельзя планировать одной формулой без длины периода.
- Прогон на большее число `--workers` быстрее (линейно до ~8 воркеров на
  проверенном профиле), но пропорционально дороже по памяти — выбирать
  `--workers` по доступной памяти хоста, а не по числу его ядер.
- `--rotate-bytes` — предел размера файла до ротации (актуально при долгих
  прогонах: ограничивает объём одного `.csv.gz` до архивации).

## Поставка в реестр контура (адрес — из инсталлятора, НЕ выполнять без владельца)

Адрес реестра и формат имени образа взяты из
`batch-scoring-installer/installer/roles/bs_cdr_gen/defaults/main.yml:96-102`
(переменные `bs_cdr_gen_image_registry`/`_name`/`_tag`/`_digest`) — так
контур сегодня адресует питоновский образ `qa/cdr-generator`. Для rust-версии
по аналогии:

```bash
# Тег под контур — по образцу питоновского qa/cdr-generator:0.1.0-py3.11,
# третья компонента тега называет рантайм; здесь это версия крейта (Cargo.toml).
docker tag rs-cdr-generator:contour-test nexus.bs.internal/qa/cdr-generator-rs:5.1.0-rust

# Push — ТОЛЬКО с разрешения владельца, не выполнялось.
# Физический адрес Nexus на отладочном контуре (не «nexus.bs.internal» —
# это манифестовое имя, резолвится через containerd-зеркала):
#   https://prod-nexus001.infra.1f4u.com/repository/onef-docker
docker push nexus.bs.internal/qa/cdr-generator-rs:5.1.0-rust
```

🔴 Имя репозитория (`qa/cdr-generator-rs`) и тег — не согласованы с владельцем
и не взяты из готовой переменной: `bs_cdr_gen` сейчас знает только про
питоновский образ, отдельных `bs_cdr_gen_rust_image_*` в роли нет. Это
предложение по аналогии, а не факт из инсталлятора — при заведении отдельного
имени решение по имени репозитория и тегу принимает владелец/директор
инсталлятора, не этот репозиторий.

## Отличие от питоновского `cdr-generator`, который использует роль `bs_cdr_gen`

- **Другой бинарник.** Питоновский образ `qa/cdr-generator:0.1.0-py3.11`
  (`installer/roles/bs_cdr_gen/defaults/main.yml:97-98`) — CPython, этот —
  нативный `rs_cdr_generator` (33.5 МБ, статически подтянутый только к
  системной glibc `debian:bookworm-slim`, сети при запуске не требует).
- **Другие флаги CLI.** У rust-версии два раздельных шага —
  `generate-subscribers` (база абонентов в `redb`) и `generate-cdr` (сама
  генерация с `--subscriber-db`); у питоновской, по `demo/generator/README.md`,
  разбивки на такие подкоманды нет. Общий конфиг (`--config path.yaml`)
  подключается тем же принципом «CLI override поверх файла».
- **Формат вывода совместим по контракту.** Тот же `CDR_{ne_id}_{date}.csv.gz`
  и тот же набор колонок CSV (проверено смоук-прогоном ниже) — партиционирование
  по `ne_id`/дате и путь `<out>/<ne_id>/CDR_<ne_id>_<date>.csv.gz` совпадают.
- **🔴 Взаимозаменяемость НЕ подтверждена.** Сверка данных питон↔rust
  не завершена — по состоянию на 2026-09-08 идёт проверка по типам трафика,
  в частности не выяснено, совпадает ли в rust-версии доля SMS с той, что
  у потребителя (SMS — 20.2 % набора у потребителя). Смоук этой сборки
  (50 абонентов, 2 суток) SMS-записи произвёл (`mo_sms`/`mt_sms` есть в
  выводе), но это не заменяет сверку долей и распределений. **Замена
  питоновского генератора в `bs_cdr_gen` этим образом сейчас НЕ предлагается,
  роль не трогалась.**
