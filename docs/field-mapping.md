# Соответствие полей CDR — rust ↔ питоновский эталон

Эталон: `demo/generator/upstream/cdr_generator/` в репозитории
`batch-scoring-installer` (не править, только читать) —
`models/cdr.py` (CDR_FIELDS, модель записи), `writer/csv_writer.py`
(имя файла, разделитель, gzip).

Порядок колонок — `CDR_FIELDS` из `models/cdr.py`, воспроизведён в
`src/writer.rs` константой `CDR_FIELDS` и структурой `EventRow`
(поля идут в том же порядке, что и колонки).

правдоподобное значение. Все такие поля перечислены в таблице выше.

## serving_ne_id — упрощение относительно эталона

В питоне `serving_ne_id` — поле модели АБОНЕНТА
(`assets/models.py:38-47`), присваивается один раз при генерации
состава через `tac_to_ne` (соответствие TAC соты → сетевой элемент,
`assets/generator.py:_build_tac_to_ne_map`) и держится за абонентом
на всех его событиях.

В rust-генераторе топологии нет вовсе: `cells.rs` не хранит TAC,
`cell_id` для КАЖДОГО события выбирается случайно
(`generators.rs`, `rng.gen_range(10_000..100_000)` и т.п.), без
привязки к соте предыдущего события того же абонента. Заводить
подсистему топологии (TAC, покрытие сот сетевыми элементами) в эту
порцию не должны — по заданию это следующий этап (нет даже вложенного
конфига `network.elements`/`network.cells`, он появится в этапе 2).

Решение этапа 1 — **распределяем НЕ по соте события, а по абоненту**:
`assign_ne_id(msisdn, network_elements)` — детерминированный хеш
MSISDN абонента по модулю списка `network_elements` (флоский список
в `Config`, этап 2 заменит источник на `network.elements[].id`
вложенного конфига). Это сохраняет содержательный инвариант,
важный для партиций: **тот же абонент всегда попадает в один и тот же
NE**, независимо от того, в какой соте его застало конкретное событие
— так же, как в питоне, только без реального TAC-джойна.

Отличие от питона: функция чистая от MSISDN и не персистится в
redb-базе абонентов — переигрывается одинаково при каждом запуске
без миграции схемы базы. Наблюдаемое поведение (стабильная привязка
абонента к одному NE) то же самое.

Полная TAC-based топология — задача следующего этапа вместе с чтением
вложенного `network.*` конфига.

## Одна data-запись вместо пары SGW+PGW

Питон на каждую data-сессию создаёт ДВЕ записи с общим `charging_id`
и одинаковыми объёмами — `sgw_data` и `pgw_data`
(`generators/data.py`, `_create_sgw_pgw_pair`; отмечено и в
`demo-cdr.yaml` как «одна data-сессия даёт ДВЕ записи»). Rust
генерирует одну data-сессию как одно событие — эмитим один
эквивалент `pgw_data` со всем объёмом трафика на нём, `charging_id`
пуст (в rust не ведётся). Дублирования нет, но нет и второй стороны
пары — если анализ явно опирается на факт парности, это нужно
учитывать отдельно.

## Ограничение этого этапа: `writer_tasks` только 1

Партиционирование вывода теперь идёт по паре (ne_id, дата) — внутри
КАЖДОЙ writer-задачи независимо (`src/writer.rs`, `EventWriter`
держит по одному открытому файлу на каждый встреченный `ne_id`).
Маршрутизация событий к writer-задачам осталась прежней:
round-robin по индексу воркера (`src/main.rs`), а не по `ne_id`.

Если запустить с `writer_tasks > 1`, разные задачи могут независимо
получить события с одинаковым `ne_id` и НЕЗАВИСИМО открыть и
перезаписать один и тот же файл `CDR_{ne_id}_{date}.csv.gz` —
тихая порча данных. Починка требует маршрутизации событий к
writer-задаче по `ne_id` вместо текущего round-robin по воркеру —
это правка архитектуры параллелизма, сознательно оставленная
следующей порции.

Поэтому `main.rs` сейчас **жёстко отказывает** при `writer_tasks > 1`
понятным сообщением, а не молча продолжает с риском коллизии.
Гоняйте генерацию с `writer_tasks=1` (по умолчанию auto-detect даёт
`workers/2`, так что при `workers=1` тоже получится 1).

## Формат файла

- Имя: `CDR_{ne_id}_{date}.csv.gz`, дата в формате `YYYYMMDD` —
  как в питоновском `_resolve_path` (`writer/csv_writer.py`).
- Путь: `<out_dir>/<ne_id>/CDR_{ne_id}_{date}.csv.gz` — как у
  питоновского `CSVWriter`.
- Разделитель — `,` (был `;`).
- Формат — gzip, вне зависимости от `--compression` CLI-параметра
  (он не относится к формату контура).
- Без ротации по размеру и без part-файлов: у эталона файл на
  (ne_id, день) всегда один.
- Заголовок — фиксированный порядок `CDR_FIELDS`, терминатор строки
  CRLF (как у Python `csv` модуля по умолчанию).

Проверено: `src/writer.rs::tests::header_matches_python_reference_format`
и разовое сравнение побайтово с эталонным `models.cdr.CDR_FIELDS`
(см. отчёт по этапу 1) — заголовок совпадает.

## Найденный попутно дефект (не в области этой правки)

При тестировании обнаружено рассогласование между
`generate-subscribers` и `worker_generate_redb_chunked`
(`src/generators.rs`, редб-путь генерации CDR, единственный
достижимый через CLI `generate-cdr`): `generate-subscribers`
(`subscriber_db_generator.rs`, `gen_msisdn`) присваивает абоненту
СЛУЧАЙНЫЙ 7-значный номер в пределах префикса, а
`worker_generate_redb_chunked` при поиске абонента по индексу
вычисляет ожидаемый MSISDN ДЕТЕРМИНИРОВАННО
(`msisdn = prefix*10_000_000 + (sub_idx % 10_000_000)`) и ищет его
в redb-базе по точному совпадению. Совпадение почти никогда не
происходит (1 к ~10 000 000 на абонента), поэтому обычный прогон
`generate-cdr` с базой из `generate-subscribers` не генерирует
событий вовсе (`0 events written` в тестовом прогоне на 20
абонентах). Не чинил — вне области этапов 1–2, для критерия
готовности этапа 1 использован прямой тест писателя
(`header_matches_python_reference_format`) в обход этого пути.
