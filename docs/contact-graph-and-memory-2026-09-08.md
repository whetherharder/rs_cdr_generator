# Сверка графа контактов с питоном и зависимость пика памяти от числа абонентов

Замер 2026-09-08, ветка `feature/contour-compat`, коммит на момент замера —
`68d4559`. Скрипт сверки — `tools/graph-compare.py`, воспроизводится им же.

## Находка 0 — `served_msisdn` у питона нельзя использовать как границу
«кто абонент», даже без аномалий

У upstream-генератора (`demo/generator/upstream` в `batch-scoring-installer`,
только чтение) секция `anomalies` включена по умолчанию
(`cdr_generator_config.yaml:436` `enabled: true`; `orphaned_records` —
`:451-453`, rate 0.02; `timestamp_anomalies` — `:455-458`, rate 0.003;
`duplicate_records` — `:441-444`, rate 0.005; `missing_fields` — `:446-449`,
rate 0.01; `corrupt_values` — `:459-462`, rate 0.002). На прогоне
2000 абонентов / 60 суток это дало `served_msisdn` **27450** различных
значений вместо 2000 реальных (в 13.7 раза больше) и записи с
`event_timestamp` за пределами заказанного периода на **~25 суток**
(файл `CDR_msc-01_20250301.csv.gz` содержит записи с датами вплоть до
2025-03-26).

Проверка с `--override anomalies.enabled=false` **не устранила** раздутие:
`served_msisdn` всё равно даёт 27654 значения. Причина другая: поле
`served_msisdn` в части записей заполняется номером из пула
`external_numbers` (`+1212...`, `+7495...` и т.п. — 6 префиксов, конфиг
`:340-347`), а не только реальным абонентом. Прямая проверка (сравнение
множества `served_msisdn` из вывода с реальным списком MSISDN из
`subscribers.json` ассетов) показала: из 13623 уникальных `served_msisdn`
в выборке 11623 (85%) — внешние номера, ни один не входит в список из
2000 реальных абонентов.

**Вывод: чтобы построить граф "абонент-абонент", питоновский вывод нельзя
фильтровать по `served_msisdn` — нужен явный список реальных MSISDN
(`subscribers.json` ассетов или свой список из конфига генерации)**;
`tools/graph-compare.py` поддерживает это флагом `--known-subs-python`.
У rust того же дефекта нет: `served_msisdn` совпадает с известными
абонентами почти полностью (1976 из 2000 базы — не участвовавшие в
звонках за период просто не встретились ни разу, это не аномалия).

**У rust аномалий нет вовсе** — `grep -rn anomal|orphan src/` находит
только два комментария (`src/contour.rs:8`, `:20-21`): секция `anomalies`
конфига явно вынесена «вне области этапа», читается как непрозрачный YAML
и не порождает никаких искажённых записей. Это не дефект rust (аномалии не
входили в задание этапа), но следствие для потребителя данных: датасеты
rust и python **не взаимозаменяемы даже структурно** — один содержит
намеренный шум (сироты, дубликаты, испорченные значения, будущие
таймстампы), другой нет. Если аналитик тестирует устойчивость пайплайна
к грязным данным на python-выборке, а фичи считает на rust-выборке (или
наоборот) — результат будет не про то же самое.

## Задача 1 — сверка графа контактов

Оба прогона: 2000 абонентов, 60 суток (2025-01-01…2025-03-01/02),
seed 42. Питон — дважды: «чисто» (`anomalies.enabled=false`) и «по
умолчанию» (аномалии включены, как и приезжает клиенту сегодня); rust —
один прогон, `--workers 2`. Фильтр — явный список реальных MSISDN
с обеих сторон.

| Метрика | python, чисто | python, по умолчанию | rust |
|---|---|---|---|
| Внутренних абонентов | 2000 | 2000 | 1976 |
| Call-записей (обе стороны — абонент) | 432260 | 430658 | 573088 |
| Пар с ≥1 звонком | 102672 | 102672 | 266425 |
| Медиана веса пары | 2.0 | 2.0 | 2 |
| Средний вес пары | 4.21 | 4.19 | 2.15 |
| Максимальный вес пары | 134 | 135 | **8** |
| Доля пар с 1 звонком | 15.0% | 16.4% | **0.0%** |
| Доля пар с 2–5 | 76.4% | 75.1% | 99.6% |
| Доля пар с 6–20 | 4.3% | 4.2% | 0.4% |
| Доля пар с 20+ | **4.3%** | **4.3%** | **0.0%** |
| Доля взаимных пар (A→B и B→A) | **1.2%** | **1.2%** | **100%** |
| Уникальных собеседников/абонента, медиана | 103 | 103 | 270 |
| Уникальных собеседников/абонента, диапазон | 51–208 | 51–208 | 214–319 |
| Устойчивость top-5 между половинами периода (mean Jaccard) | **0.632** | 0.580 | **0.002** |

### Вывод — прямо

Данные rust **непригодны как замена питоновским** для фич по кругам
общения `CircleTop`/`CircleAvgWeighted`, и расхождение системное, а не
шумовое:

1. **Вес контакта у rust размазан почти идеально ровно** (99.6% пар — от
   2 до 5 звонков, максимум 8 на пару за 60 суток), у питона — выраженный
   длинный хвост (4.3% пар — 20+ звонков, максимум 134–135). `CircleAvgWeighted`
   на rust-данных выйдет у всех абонентов примерно одинаковым, у питона —
   разным и содержательным. Это и есть главный риск, названный в задании,
   и он подтвердился.
2. **Граф rust почти полностью симметричен (100% взаимных пар), граф
   питона почти полностью асимметричен (1.2%)** — прямое следствие
   `contact_book.asymmetric: true` в конфиге питона, которого в rust,
   судя по результату, нет вообще (модель контактной книги упрощена до
   симметричной или направление A→B/B→A не разносится).
3. **Круг общения у rust не наследуется между половинами периода
   (Jaccard 0.002 — практически ноль), у питона наследуется ощутимо
   (0.632)**: у rust контактная книга каждого абонента похоже
   пересобирается заново на каждый вызов/период, а не хранится как
   устойчивая сущность. Это ровно тот сценарий, от которого предостерегает
   задание: «если круг пересобирается каждые сутки заново, фичи по нему
   будут шумом» — здесь так и есть.
4. Число уникальных собеседников на абонента тоже разошлось на порядок
   иначе, чем ожидалось (у rust медиана 270 против ранее заявленных
   «2..25, медиана 11» — другой объём выборки, здесь 2000 абонентов и
   60 суток, а не прежний прогон; но и без сравнения с прежним числом
   разброс 214–319 у rust против 51–208 у питона на одинаковых входных
   данных сам по себе говорит о разной модели: rust почти не выбирает
   контакты избирательно.)

Аномалии на выводе почти не сказались (чистый и боевой прогоны питона
дали одинаковые метрики) — значит проблема не в грязных данных, а
в базовой модели контактной книги.

## Задача 2 — зависимость пика памяти от числа абонентов

Гипотеза линии аналитика (постоянная часть памяти — пул абонентов и
справочники, поток пишется без накопления, потолок задаётся числом
абонентов) — **проверялась и отклоняется**.

Фиксировано: 8 суток, `--workers 2`, seed 42. Замер — `/usr/bin/time -l`,
поле `maximum resident set size`.

| Абонентов | Записей (8 суток) | Пик RSS | Байт/запись | Байт/абонента |
|---|---|---|---|---|
| 5 000 | 913 083 | 431 398 912 (411 МиБ) | 472.5 | 86 280 |
| 20 000 | 3 653 795 | 1 216 991 232 (1160 МиБ) | 333.0 | 60 850 |
| 80 000 | 14 604 300 | 1 721 831 424 (1642 МиБ) | 117.9 | 21 523 |

Рост абонентов 4× (5000→20000) дал рост RSS в 2.82×, следующий рост 4×
(20000→80000) — в 1.42×. **И байт/запись, и байт/абонента убывают** с
ростом числа абонентов — тот же сублинейный профиль, что уже
задокументирован в README для роста по суткам, а не пропорциональный
рост, которого требует гипотеза.

**Вывод — прямо: пик памяти растёт значительно медленнее, чем число
абонентов, и «байт на абонента» не является константой — планировать
через неё нельзя.** Постоянная часть (пул абонентов и справочники) —
не единственный крупный вклад в память; правдоподобнее, что пик держится
на буферизации потока записей (шардированный писатель, судя по логу
`Writer task for shard 0 completed: N events written`), которая растёт
с объёмом данных, но не линейно и не только от числа абонентов — при
фиксированных 8 сутках объём данных тоже растёт пропорционально
числу абонентов (записей/абонента ≈182.6, постоянно на всех трёх
точках), то есть рост RSS сублинейный **относительно объёма данных
тоже**, а не только относительно числа абонентов. Раздельно развести
вклад «число абонентов» и «объём потока» в этом замере нельзя — они
менялись синхронно; для этого нужен отдельный прогон с фиксированным
числом абонентов и варьируемым числом записей на абонента (не
сделан, ограничение по времени).

## Что не сделано

- Не раскопана причина попадания внешних номеров в `served_msisdn`
  у питона на уровне исходного кода (`cdr_generator/generators/*.py`) —
  зафиксирован факт и масштаб, не первопричина.
- Не разведён раздельно вклад «число абонентов» и «объём потока записей»
  в пик памяти (см. вывод задачи 2) — нужен отдельный прогон с
  фиксированными абонентами и переменным объёмом.
- SMS-записи исключены из графа контактов: в этом прогоне upstream не
  выдал ни одной SMS-записи (`mo_sms`/`mt_sms` count = 0 при ненулевых
  lambda в конфиге) — отдельный дефект/расхождение, не разбирался.
